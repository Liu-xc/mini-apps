# it-008 · 吃喝玩乐：分类体系 + 想吃/想玩愿望清单

- **状态**：已完成（2026-09-20 实施，与 it-007 同批入库；it-009 评审时同步状态标记）
- **提案日期**：2026-09-20
- **范围**：Place 新增一级分类（吃/喝/玩）与愿望标记；抽签页升级为「今天干啥」；愿望的种草→拔草闭环与轻量排期。不改抽签算法、不改存储结构（向后兼容字段新增）
- **姊妹迭代**：wardrobe it-019（想买愿望清单），同源需求（Leo 2026-09-20）：「把想吃的和想买的也加进来，可以进行预览、规划；吃啥太窄了，应该包含吃喝玩乐」

## 背景与动机

App 定位是「今天吃啥」，但生活决策不止吃——看场电影、爬个山、约桌游，现在完全录入不了；「吃喝玩乐」里只覆盖了一个字。另一方面，种草了还没去的地方没有承载地：录进来就是一条普通条目，和「随手记的老店」无区分——列表里看不出「这是我想去的」，抽签池里也分不出「想去尝鲜」和「吃过觉得还行」。

三件事补齐：

1. **分类体系**：条目分 吃/喝/玩 三类，抽签页从「今天吃啥」变成「今天干啥」，娱乐项目进池子。
2. **愿望清单**：先种草（还没去过）的条目有明确标记与专属视图；去了（记一笔）自动拔草，形成 种草→抽取→体验→落账 闭环。
3. **轻量排期**：愿望可安排到某天（「周末去那家展」），当天抽签页顶部提示。

## 方案

### 阶段A · 分类体系（吃 / 喝 / 玩）

- 数据模型：`Place.category: PlaceCategory = EAT | DRINK | PLAY`，默认 `EAT`；旧 JSON 缺字段反序列化为 EAT，**不 bump schemaVersion**（同 wardrobe it-017 `refImageFile` 先例）。
- **kind 语义泛化**（ADR-012）：枚举值不变（RESTAURANT/TAKEOUT/HOME，磁盘零迁移），从「怎么吃」泛化为「在哪进行」，显示文案与可选项按 category 适配：

| category | kind 选项（显示文案） | 说明 |
|---|---|---|
| EAT 吃 | 堂食 / 外卖 / 自做 | 原样不动 |
| DRINK 喝 | 堂食 / 外送 / 自调 | 枚举同 EAT，仅文案差异 |
| PLAY 玩 | 出门 / 在家 | TAKEOUT 选项不出现（数据层面 PLAY+TAKEOUT 为无效组合，录入 UI 不给） |

- 地图 marker 颜色改按 **category** 着色：EAT=红 / DRINK=琥珀 / PLAY=紫；吸顶图例同步；kind 保留在摘要卡内展示。
- W4 表单：新增「分类」单选 chips（吃/喝/玩，默认吃，置于「类型」之前）；kind chips 文案随分类切换。
- W1 抽签页 & W3 列表 & 筛选弹层：类型 chips 前增加分类 chips（全部/吃/喝/玩，同一横滑行）。
- W1 标题随分类动态：全部→**今天干啥** / 吃→今天吃啥 / 喝→今天喝啥 / 玩→今天玩啥。
- 演示数据：`tools/demo-data.sh` 增补喝/玩条目（咖啡馆、电影院、桌游吧、公园…）；it-006 mock 仓库种子同步。

### 阶段B · 愿望清单（想吃 / 想玩）

- 数据模型：`Place.wishlistedAt: Long?`（种草时间；null = 常规条目），向后兼容同上。
- W4 表单新增「🌟 先种草（还没去过）」开关；愿望条目仍仅名称必填，其余全可选。
- W3 列表：筛选弹层加「只看愿望」开关；愿望行带 🌟 标记；排序新增「种草时间」（倒序）。
- W5 详情：愿望条目显示「种草于 x 天前」徽章；**拔草闭环**——点「记一笔」落账成功后自动移出愿望，snackbar 提示「已移出愿望清单 · 撤销」。
- W1 抽签页新增「只抽愿望」开关（默认关，与「排除最近」并排）：开启后候选池 = `wishlistedAt != null` 且通过分类/类型过滤的条目；「排除最近 N 天」对愿望池天然无命中（都没去过），逻辑不改。结果条「就吃这个」随分类显示「就吃 / 就喝 / 就去，安排！」。

### 阶段C · 安排（轻量排期，可裁剪）

- 数据模型：`Place.planAt: Long?`（想去/想吃的日期，可空，仅对愿望条目提供入口）。
- W5 详情 / W3 列表长按菜单：「安排到某天」→ 日期选择器（MVP 不做日历视图）。
- W3 愿望视图：已安排的愿望置顶为「最近的安排」小节（按日期升序）；已过期的静默回到普通愿望序。
- W1 抽签页顶部：当天有安排时显示提示条「今天安排了：巷子深火锅 →」点击进详情；「只抽愿望」开启时安排条目自动进池。

## 与 it-007（统计回顾）的关系

it-007 的统计口径是吃专属（「286 顿」、类型占比=堂食/外卖/自做）。**建议本迭代先行**：it-007 实施时按 category 一次把口径做对——EAT 计「顿」、DRINK 计「杯」、PLAY 计「次」，占比维度改分类/类型双层。若 it-007 先实施，本迭代落地后 it-007 需返工口径，成本更高。

## 验收标准

- 抽取过滤：分类 × 类型 × 愿望开关的组合过滤、动态标题、结果条文案（JVM 单测，含全组合矩阵与空池边界）
- 拔草：落账后自动移出愿望、撤销恢复 wishlistedAt 原值（单测）
- 安排：设置/清除 planAt、置顶排序、当天提示条出现与消失（单测 + 模拟器实测）
- 旧数据兼容：无 category/wishlistedAt/planAt 字段的旧 JSON 加载后 == EAT/常规件，抽签列表行为与升级前一致（单测）
- 地图：三色 marker 与图例一致；无坐标条目入口不受影响
- `./gradlew assembleDebug test` 通过；演示模式（it-006）含喝/玩种子数据，截图对照验收

## 开放决策点（请 Leo 圈）

1. **喝要不要独立成类**？我建议独立（奶茶咖啡外送高频，marker/统计/抽签筛选都有意义），成本只是一个 chip；也可以并入吃做两类（吃/玩）。
2. **「安排」阶段C 进不进本期**？（可裁剪；愿望+抽签联动已是完整闭环，排期是锦上添花）
3. kind 文案泛化（堂食→出门/自做→在家）与 marker 改按 category 三色——OK？
4. App **launcher 显示名「吃啥」暂不改**，仅页内文案动态（今天干啥）——还是连桌面名一起改？（改名牵连桌面图标名/README/演示模式文案，建议观望，定位语在 README 与 00-overview 调整即可）
